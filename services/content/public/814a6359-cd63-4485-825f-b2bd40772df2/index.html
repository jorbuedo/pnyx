1The problem

Governance communities in the Cardano/Midnight ecosystem need somewhere to talk that has three properties no existing forum has at once:

  1. The wallet is the identity. No email, no OAuth, no account server. Portable and seed-recoverable.
  2. Entry can be gated on a fact about you without revealing you. “I hold ≥ X”, “I’m a registered DRep”, “I work at Org Y”, “I’m a unique human”, “I’m over 18” — proved, not asserted, and not doxxing.
  3. The same person can be disclosed in one community and anonymous-but-verified in another, and those two contexts are mutually unlinkable — including by the operator of the service.

Point 3 is the load-bearing requirement. Everything else in the design exists to satisfy it.

Why this needs a chain

If a server enforces membership, uniqueness and bans, then the server knows the mapping and privacy is a promise, not a property. If a single Midnight address signs every action, everything is linked to one public key and requirement 3 fails outright. What makes the claim honest is that the trust-critical state — who is a member, who has already joined, who has already voted, who is banned — lives in a public contract that anyone can verify, while the secrets that link those facts to a person never leave the device.

What Community deliberately does NOT claim. Midnight buys verifiable membership, uniqueness, gating, tallies and moderation. It does not buy message confidentiality: post bodies live off-chain in our own store, and the operator can read them. Confidential messaging is a separate app-layer problem (X25519 sealed envelopes, §4.5) and is never marketed as “Midnight privacy”.

│ seed → forumRoot             │  │ member tree (Merkle)       │  │ communities, channels,    │
│  ├ per-community personas    │  │ join + action nullifiers   │  │ posts, poll bodies        │
│  ├ credential secrets        │─▶│ gate policy per circle     │◀─│ realtime, push            │

│    (Rust, on-device)         │  │ bans                       │  │ never enforces membership │
└──────────────────────────────┘  └────────────────────────────┘  └───────────────────────────┘
                                     fees sponsored (DUST) — users hold no funds

Three rules keep the story coherent:

  • The chain enforces possession and uniqueness; issuers vouch for meaning. A circuit can prove you hold a credential secret whose commitment is in the tree. It cannot know that “DRep” means anything — a registrar attests that, once, at registration.
  • The content plane is a cache, never an enforcer. It mirrors public contract state so the UI is fast; any client can re-verify against the chain.
  • Witnesses never leave the device. Personas, gate secrets and ballots are private inputs to circuits proved on the phone. The backend only pays the DUST fee.

Product vocabulary

The UI never says “circle”, “persona” or “nullifier”. Circles render as communities, threads as channels, proposals as polls, personas as a per-community display name. This document uses the internal words because the contract does.

3Identity — the “passport”

Name collision, worth stating once. Midnight Passport (midnightntwrk/passport) is IOG’s own identity project — Apache-2.0, pre-product, ~Oct-2026 MVP target. It is not a dependency (no releases, no tags, real code on branches) — but it is largely a written specification, and we intend to conform to it where it fits rather than merely borrow from it. See §4.7. “Passport” below means our identity surface — the app’s Id tab — unless it says Midnight Passport.

3.1 Derivation tree

seed  (enclave-held, biometric-gated, passkey-PRF recoverable)
 └─ forumRoot = HKDF(seed, "pnyx:root:v1")
     ├─ persona   sk_C  = HKDF(forumRoot, "pnyx:persona:v1:" ‖ circleId)   → one per community
     ├─ credential secret = HKDF(forumRoot, "pnyx:cred:v1:" ‖ claimTag)    → one per claim
     └─ encryption key (X25519)                                            → sealed DMs

Every persona and every credential secret is derived, so a reinstall re-derives the whole identity; Merkle paths are re-fetchable from public state. This is what makes an identity built on non-recoverable contract private state actually recoverable.

3.2 Two nullifier families — the trick that resolves Sybil vs. unlinkability

Nullifier Preimage Enforces Unlinkable across
Join JN_C H("pnyx:jn:v1", circleId, gateSecret) one scarce unit (credential / invite / human) → one persona per community communities
Action AN_{a} H("pnyx:an:v1", actionId, sk_C) one persona → one vote per poll polls and communities

The join nullifier must bind to whatever the gate makes scarce. A secret the user can mint for free bounds nothing — so open communities are explicitly weak (personas there are cheap; a ban only costs the banned party another join fee) and we say so in the product. Strong trust is a gated community, by definition.

Ban the nullifier, not the person. Moderation inserts JN_C into a banned set: the same credential-holder cannot re-enter under a fresh persona, and nobody learns who they are. Ban-resistance without de-anonymisation — a feature of the model, not a compromise.

3.3 Disclosure levels, chosen per community at join time

  1. Public — persona linked to the mn_addr profile (opt-in doxxed).
  2. Verified-anonymous — persona plus ZK-verified claims, no identity linkage.
  3. Plain-anonymous — persona only.

4.1 Membership — creating and joining communities

Intent Proves Reveals K Status
createCircle(gateCommitment) nothing private; registers a community and its gate policy circleId, gate commitment 9 live
joinOpenCircle(circleId) knowledge of a persona secret; not already joined; not banned join nullifier, member leaf 14 live device-proven end-to-end
joinCircle(circleId) — invite gate knowledge of the invite secret behind the circle’s gate commitment; not already joined; not banned join nullifier, member leaf 15 live server-proved
joinCredentialedCircle(circleId, claimTag) Merkle-inclusion of an attested credential commitment + nullifier bound to the credential secret join nullifier, member leaf, the public claimTag ~13–15 est. to write the real gated-community story
joinByDeposit(circleId) a deposit / soulbound membership token received into the circle vault join nullifier, member leaf est. to write the only trustless holdings gate available today

The membership proof is the canonical Midnight pattern: HistoricMerkleTree inclusion plus a domain-separated nullifier. Historic roots are accepted, so concurrent joins do not invalidate an in-flight proof — exactly the concurrency property a live forum needs.

Why joinByDeposit and not “prove you hold X”: a Compact circuit today cannot read a user’s balance, cannot read Cardano state, and cannot verify an external signature in-circuit. Passive holdings proofs are therefore impossible on Midnight right now. The workable trustless gate is deposit-into-a-vault; anything about another chain needs a registrar (§4.4). This is a dated platform constraint, and the design keeps it behind a swappable seam.

Ballot secrecy v1 is commit/reveal — the pattern from Midnight’s own Election contract. The poll body lives off-chain; its commitment is anchored on-chain, so a tampering operator is detectable.

Product knob: as specified every vote is on-chain and costs DUST. Casual off-chain polls (persona-signed, uniqueness enforced by the content plane) are cheap to add but lose the trustless tally — a per-poll choice, not a global one.

4.4 Credentials and selective disclosure

This is the layer that turns “a forum with anonymous accounts” into “a forum where you can prove things about yourself without being identified”. It is the largest remaining piece. 

off-chain proof (signature / VC / on-device ZK)  ─┐
                                                  ├─▶ registrar verifies MEANING
user-computed commitment H(claimTag, credSecret) ─┘   └─▶ registerCredential → identityTree

later, per gated community:
  joinCredentialedCircle proves Merkle-inclusion of that leaf
  + emits a nullifier bound to credSecret  ⇒ one credential = one persona per community

Claims we want to support, and what each honestly costs

Claim Regime What the registrar learns Chain sees
“I’m a Cardano DRep” registrar + indexer (CIP-95 DRep key, CIP-8 signature, indexer confirms registration) DRep ID ↔ commitment, at time T a nullifier
“I hold ≥ X ADA” registrar + indexer (snapshot at T) Cardano address ↔ commitment a nullifier
“I hold ≥ X on Midnight” trustless — deposit / soulbound membership token nothing a nullifier
“I’m a unique human” on-device passport-ZK (Self / zkPassport / Rarimo); registrar checks the document nullifier is unseen a document nullifier, no PII a nullifier
“I’m over 18” on-device ZK range proof (best) or an SD-JWT age_over_18 boolean (pragmatic) on-device: nothing; SD-JWT: issuer linkage a nullifier
“I work at Org Y” issuer-signed VC → registrar issuer identity ↔ commitment a nullifier

The honest trade-off, stated in-product: for anything the chain cannot check itself, a registrar learns real-id ↔ commitment once, at registration. Post-registration anonymity holds even against registrar and server collusion — but that one linkage exists. When in-circuit signature verification lands in Compact, the registrar step collapses into the circuit and these become fully trustless; the design keeps it behind that seam.

Cardano wallet posture: for Cardano-linked claims the app is a connect-only CIP-30/95 client against the user’s existing Cardano wallet — getUsedAddresses, getPubDRepKey, signData. It never calls signTx, submitTx or getUtxos, so it cannot move funds and custodies no Cardano keys. Balance facts come from a first-party-configured indexer, never from wallet-reported balance.

The decision gate that was open here is effectively settled by conforming (§4.7). The Midnight VC spec’s claim-representation.md is normative draft material that classifies every credential field as public / selectivelyDisclosed / committedPrivate / predicateOnly inside a Compact-native VC<...> envelope, and positions SD-JWT as an export adapter rather than the engine — which is the direction we were already leaning. Adopting that taxonomy means our claimTag + credential commitment become their claim-commitment shape, and the four rows above get a written data model instead of an invented one.

4.6 Contract hardening required before a real network

These are known, recorded holes in the spike-lineage contract — each is a contract intent in its own right:

  1. Per-proposal tallies instead of two contract-global counters.
  2. Gate addModerator behind a maintenance authority or governance path.
  3. Network ID in nullifier domain separation — otherwise nullifiers replay across preprod/mainnet.
  4. Front-running of sequential counters (createCircle, createProposal): our submission queue serialises our transactions only; a public contract accepts anyone’s. Any invariant that relies on the queue is not an invariant.
  5. Maintenance-authority policy — circuitMaintenanceTx rotates verifier keys and contractMaintenanceTx transfers authority. A “credibly neutral” forum with an upgrade key is only as neutral as the keyholder. Multisig, burn: unpinned.
  6. Independent audit before mainnet.

4.7 Compatibility with Midnight Passport

Passport is pre-product, but it is not only demos: much of it is written specification, and where a spec exists we should implement it rather than something adjacent to it. Conforming costs us nothing extra — these are circuits we have to write anyway — and it keeps a future handoff or interop story open instead of forking the ecosystem’s identity layer on day one.

“Passport-compatible” is not one thing, though. Four surfaces, four verdicts:

Surface What exists Verdict
VC claim model + revocation + credential status — midnight-verifiable-credentials/docs/spec/ (10 documents, normative MUST/MUST NOT, a written conformance.md defining conformance categories, hidden-holder-interoperability.md), plus real revocation-registry.compact / status-proof-protocol.compact draft spec + prototype contracts Conform. Highest value, and it settles §4.4’s decision gate
Encrypted inbox envelope — 192-byte container, version=0x01‖suite=0x01, X25519 + HKDF-SHA256 + AES-256-GCM, info string midnight:custody:inbox:v1 byte-level format + reference impl Byte-compatible for free. We reimplement the crypto on @noble for Hermes regardless; keeping the framing means a Passport wallet could one day read our envelopes
<handle>.night identity registry demo-grade contract (49 lines) Conform to the shape, diverge on the referent. Theirs binds handle → custody account; we have no custody account, so ours binds handle → persona / mn_addr. Their demo also permits re-registration with no ownership gate — ours must gate it
Account custody + device-auth (MIP-0012/0013) reference contracts + passing conformance evidence Not now. Orthogonal to identity-not-funds, and it is a JubJub-Schnorr rail against our BIP-340/secp256k1 SIWM — a second signing rail, not a drop-in

The design tension to keep in view. Passport’s north star is “scan a QR → a working, human-named account, with no seed phrase / address / gas ever shown”. A human-named account is the opposite of an unlinkable persona. The two compose — a named account is exactly our “public” disclosure level (§3.3) — but naming cannot become our universal identity anchor without breaking §1’s load-bearing requirement. Adopt the spec; do not silently adopt the identity model with it.

How to conform without taking a dependency. Pin to the documents and conformance suites, never to their code: there are no releases or tags, the real code sits on branches and PRs (main is an empty template), and every Compact source predates our toolchain (0.31.1) and must be recompiled and re-verified. Conversely, file our own extensions — SIWM, deriveAppSecret — into their MIP pipeline, so divergence surfaces in review rather than at integration.

Note also that Passport is not the only claimant here: did:midnight is a third-party IAMX draft (registered ≠ standardised), Passport itself defines no DID method, and Midnames is the de-facto community identity layer with real VC code that is nonetheless unpublished. “Be DID-compatible” is currently ambiguous; “be Midnight-VC-spec conformant” is not.

5Where it actually stands

Every circuit compiles and proves. Toolchain compactc 0.31.1, full compile 14.5 s.

Circuit K Prover key Proof (desktop, warm) Proof (native Rust)

banJoinNullifier 13 2.8 MB 309 ms —

joinOpenCircle 14 — — ~0.8 s (≈1.0–1.7 s on device)
joinCircle 15 9.6 MB 1,007 ms —
castVote 15 9.6 MB 1,010 ms ~1.4 s (≈2.7 s on device)

Verifier keys are 4 KB each; total artifacts ~30 MB. Peak prover memory 1.09 GiB — nowhere near the K≥18 memory wall. The cryptography was never the risk, and the measurements settled that.

End-to-end, on a real chain: deploy plus all seven circuits executed as real transactions with real proofs, final ledger state verified through the indexer, 8/8 checks. Per-call wall time 17–19 s, block-time dominated, not proving — which is exactly why the content plane writes optimistically and chain confirmation arrives asynchronously.

On-device: all four member circuits (join / vote / proposal / reveal) are ported to native Rust and bridged to Android; a device-proven joinOpenCircle landed on-chain through the real forum UI. iOS ships key derivation only — the proving C-ABI is not built yet.

Prototype product surface: 4-tab app (Id · Community · Wallets · Menu), Discord-shaped community rail / channel panel / chat, communities + channels + pinned polls, SIWM sign-in folded into a single biometric unlock, realtime content store, push notifications, passkey-PRF seed recovery, sponsored DUST fees (users hold no funds).

Known gaps, each with a named fix

This is development-stage work, and the gaps are tracked rather than papered over:

  • An interim server-side proving path is still in place. The device rail that replaces it is built and verified; deleting the interim path is a precondition for real users, and is currently waiting on an upstream ledger WASM bug in fee balancing.
  • Sybil resistance is exactly what §4.4 exists to fix — today there is nothing beyond rate limiting.
  • Chat is plaintext to the operator until sealed envelopes ship (§4.5).
  • The subject↔persona mapping held by the content plane should become client-derivable, so the server never stores it at all.

None of these are design flaws; all four are recorded, and each has a named fix above.

6Delivery order

Phase Content State
0 Public forum + Sign-In-With-Midnight done
1 Personas + on-chain membership, open/invite gates, nullifier bans, on-device proving done final flip pending
2 The credential substrate — identityTree, registerCredential, joinCredentialedCircle, built to the Midnight VC envelope + status/revocation model (§4.7); DRep and ADA attestation; deposit gates; per-proposal tallies; contract hardening next
3 Issuers and claim families on top of it — personhood, age predicates, workplace VCs; full per-community disclosure levels; identity registry planned
4 Multi-option and homomorphic tallies, persona-scoped reputation with “rep ≥ threshold” proofs, mainnet planned

Resequenced 2026-07-28. Conforming to the VC spec pulls the credential contract surface from Phase 3 into Phase 2: Phase 2 needs a registrar anyway for DRep/ADA attestation, so building it on the conformant shape rather than a bespoke commitment to be migrated later is the cheaper order. Phase 3 keeps the issuers, not the substrate.

7Why this is worth building

The contract is the credibly-neutral backend. No operator owns membership, censors the record, or can de-anonymise a user. And because identity and credentials belong to the wallet rather than to any one forum, the same credential proves you into a different forum’s contract while per-context nullifiers keep the personas unlinkable — and a shared “unique human” or “DRep” registry contract could gate many forums at once, each inheriting Sybil resistance without learning who anyone is.

That property — a shared identity substrate for the ecosystem’s governance space that nobody has to trust — is the reason to take on ZK proving on a phone. Nobody else ships a forum-shaped product on Midnight; the Merkle-plus-nullifier pattern exists elsewhere only as tutorials.
